# ADR-005: 录音资产生命周期与儿童隐私边界

## Status
Proposed（建议在**第一条真实录音入库之前**落地；当前生产 `recordings` 行数 = 0，改动成本最低）

## Context

`backend/app/api/recordings.py` 把孩子发音的原始音频落盘到 `backend/media/<child_id>/<uuid>.ext`，
元数据（路径/时长/文本/来源/评测分预留）写入 `recordings` 表，回放走家长鉴权。

**做对的部分**（本次核查确认，勿回退）：
- 归属校验严谨：`_child_belongs()` 同时校验 child→family；回放接口对 `rid` 再查一次 child_id
  并与路径参数比对，跨家庭一律 404（不泄露"存在性"）。
- 列表接口不暴露服务器文件路径。
- nginx 禁止直出 media（STABILITY.md §1），回放必须过 JWT。
- 备份脚本把 `media/` 单独打包，与部署目录分离。

**缺失的部分**：

| # | 问题 | 依据 |
|---|---|---|
| 1 | **没有任何删除接口**。孩子的声音一旦落盘，家长无法删除单条，也无法整体导出/删除 | 仅有 `POST` / `GET` / `GET .../audio`，无 `DELETE` |
| 2 | **没有保留期**。`media/` 单调增长，每日 tar 备份随之增长 | STABILITY §3：`media/` 非空即打 `media-YYYYMMDD.tar.gz`，保留 14 天备份 → 峰值约 14 × 全量 |
| 3 | **上传无大小上限**。`data = await file.read()` 整份读进内存，只校验了下限（256 字节） | 单 worker uvicorn + 40G 磁盘：一次大文件上传即可拖垮进程或打满磁盘 |
| 4 | **库里存绝对路径**。`file_path` 存的是 `str(path)`（含服务器绝对前缀） | 媒体根一旦迁移（OSS / 换机 / 灾备恢复路径不同），历史行全部指向失效路径 |
| 5 | **无单孩子配额**。反复练习同一句会不断产生新文件（列表仅显示最近 200 条） | 无 count/size 上限 |

### 为什么"现在"做

这是全仓**唯一会无限增长的敏感数据**，而且当前行数为 0。
在 0 条记录时建立生命周期，成本是"加几个函数"；在 5000 条记录时建立，成本是"设计清理策略 +
逐条确认哪些能删 + 处理历史遗留孤儿文件"。

同时，**开放注册（ROADMAP P3）会让这件事从"自家事"变成"合规事"**：孩子的语音属于敏感个人信息，
面向外部家庭提供服务时，监护人知情同意、最小必要、可删除、可导出这些要求会真实落到系统上。
本文不给出法律结论（需要专业意见），只确立一条工程原则：
**系统必须具备执行这些动作的能力**，否则再正确的政策也无法履行。

## Decision

### 1. 上传边界（立即可做，独立于其他决策）

- 增加大小上限（建议 **5MB**，参考单次跟读录音的实际量级），超限返回 413 且**在读文件前**就拒绝
  （检查 `Content-Length` + 读取时累计上限，避免把内存当缓冲）。
- 增加单孩子配额（建议 **最近 200 条或 200MB**，先到先限），超限返回 429 并提示家长清理。
- `file_path` 改存**相对路径**（`<child_id>/<uuid>.ext`），读取时与 `MEDIA_ROOT` 拼接。
  迁移：现有 0 行，无需回填；实现时加一条"读到绝对路径也能用"的兼容分支即可（防御旧数据/旧备份）。

### 2. 保留期：删音频，不删学习记录

- 默认保留 **90 天**（可配置），由现有 cron 体系每日执行。
- **关键取舍**：清理时删除音频文件并把 `file_path` 置空、标记 `purged_at`，
  **但保留 `recordings` 行与 `scores_json`**。

  理由：家长真正长期需要的是"孩子这句话越读越准"的**趋势**（分数序列），
  而不是三个月前那段听不清的 webm。音频是即时的、可再生的（重录即可）；分数是不可再生的历史。
  这个取舍让"隐私最小化"和"家长价值"同时成立，而不是二选一。

- 孤儿文件清理：按 `recordings.file_path` 反查，删除 media 下无人引用的文件
  （防止上传成功但入库失败的半成品长期滞留）。

### 3. 家长侧数据主权接口

| 接口 | 语义 |
|---|---|
| `DELETE /api/v1/children/{child_id}/recordings/{rid}` | 删除单条（音频 + 行），归属校验同回放 |
| `GET /api/v1/children/{child_id}/recordings/export` | 打包导出（zip + 元数据 JSON），家长拿得回自己的数据 |
| `DELETE /api/v1/children/{child_id}` | 删除孩子档案及其全部数据（录音/进度/奖励/事件），需二次确认 |
| `DELETE /api/v1/auth/me` | 删除家庭账号及全部关联数据 |

后两个是**开放注册的前置条件**，不要求现在实现，但要求"决策已定、形状已定"。
实现时必须：软删除优先（先标记，延迟真删），并覆盖 `media/` 与 `events`（ADR-004）。

### 4. 隐私边界落成文档

在 `docs/` 新增一份**数据清单**（不必长），逐项写清：
采集什么 / 为什么需要 / 存在哪 / 谁能访问 / 保留多久 / 如何删除。
四个数据集：`progress`、`rewards`、`recordings`、`events`（ADR-004）。

- 明确**不采集**：精确地理位置、通讯录、设备唯一标识、孩子真实姓名以外的身份信息。
- 家长门禁口令、JWT 密钥、讯飞凭据永不入 git、永不进日志（现有做法正确，写进清单固化）。

## Consequences

**变容易**
- 备份体积有上限（音频 90 天滚动 × 14 份快照），磁盘与恢复时间的增长变为可预测。
- 面对家长"能不能把我孩子的声音删掉"时，有明确、可执行、可解释的答案。
- 开放注册时不必回头补历史遗留数据。
- 上传上限顺带消除了一个低成本 DoS 面（单 worker 架构下尤其重要）。

**变难 / 新债**
- 引入"音频可被删除、分数永存"的**非对称数据模型**：读接口与 UI 需要处理"有记录但无音频"的状态
  （家长中心显示"音频已过保留期"而非报错）。这是必要成本，但必须显式处理，
  否则会表现为"点播放没反应"这种最差的失败形态。
- 90 天是**产品判断**而非技术结论：会减少"回听三个月前"的能力。若家长反馈强烈，
  应调整为"按总量封顶"（如每孩子保留最近 200 条）而不是简单延长天数——
  总量封顶对磁盘可控，天数延长的增长速度不可控。**倾向总量封顶**。
- 实现删除意味着"备份里仍有旧音频"：14 天滚动备份窗口内，被删数据仍存在于历史快照中。
  这必须在数据清单里如实写明（不能声称"删除后立即不可恢复"）。

## Alternatives considered

| 方案 | 取舍 | 结论 |
|---|---|---|
| **A. 永久保留全部录音** | 最简单；但儿童语音无限期存储、备份无限增长、无法响应删除诉求 | ❌ 与"家长信任"支柱冲突，且开放注册时是硬障碍 |
| **B. 删音频 + 留分数 + 保留期/配额（本方案）** | 兼顾隐私最小化与家长价值；需处理"无音频"状态 | ✅ **采纳** |
| **C. 完全不落盘，评测完即弃** | 隐私最优；但丢失"回听孩子成长"这一核心情感价值，也丢掉家长复盘材料 | ❌ 产品上不成立 |
| **D. 立刻上对象存储 + 服务端加密 + 签名 URL** | 长期正解；但当前 0 条记录、单机部署，引入云凭据/网络依赖/成本 | ⏸ 触发条件：`media/` > 2GB，或每日备份耗时 > 1 分钟 |
| **E. 端侧加密后上传（只有家长设备能解）** | 隐私最强 | ⏸ 需要在 H5 端管理密钥与恢复，工程量远超当前阶段收益 |

### 与 ADR-002 / ADR-003 的耦合

本 ADR 引入表结构变更（`purged_at`、`file_path` 语义）→ **依赖 ADR-002 的迁移机制**；
清理任务与 `media/` 的备份/恢复流程相关 → 落地后需同步更新 STABILITY.md §3 与 §6.2。

### 与合规的关系（需专业意见）

上文提到的"监护人同意 / 最小必要 / 可删除 / 可导出"是**工程能力的清单**，不是法律意见。
面向外部家庭收费之前，应就《个人信息保护法》与儿童个人信息相关规定取得专业意见；
本 ADR 的作用是保证届时不缺"执行能力"这一环。
