## 0. 三句结论

1. **现阶段的架构选择基本正确，不要动骨架。** 前后端分离、契约先行（OpenAPI → 生成 TS 类型）、
   离线优先 + 服务端权威合并——这三条是这类产品的正解，而且实现质量高于同规模项目的平均水平。
2. **真正的风险不在代码分层，而在"交付与数据的可复现性"。** 后端部署仍靠手工 scp、
   数据库迁移无版本、课程内容有两个事实源且无防漂移校验。这三件事会随课程数与家庭数**非线性变痛**，
   而它们的修复成本现在极低。
3. **不要现在做分布式。** 运行面真实数据是 `families 3 / children 1 / lessons 7 / progress 1 / recordings 0`。
   在这个量级上引入 Postgres、微服务、消息队列、K8s 都是**纯负债**。
   该做的是把"什么时候必须换"写成**可观测的触发条件**（§5），而不是提前换。

          │ 静态站（nginx）   │   │ FastAPI 后端        │   │ 讯飞语音评测     │
          │ /www/.../www/    │   │ 127.0.0.1:8000     │──►│ （服务端代理）   │
          │ + GitHub Pages   │   │ nginx 反代 /api     │   └─────────────────┘

### C4-L2 容器与关键内部结构

| 层 | 组成 |
|---|---|
| 客户端 | Vue3 SPA（**hash 路由**）+ PWA（SW 预缓存壳 + 媒体 cache） |
| 客户端分层 | `views/` · `components/`(layout·activities·ui) · `composables/` · `stores/`(8 个 Pinia) · `services/` · `utils/` · `data/` · `types/` |
| 交付面 A | GitHub Pages（子路径）—— 与自定义域名共用同一份 `dist/` |
| 交付面 B | 华为云 nginx 静态目录（`zelab.cn` 根路径，`build:root`） |
| 后端 | FastAPI，7 个域路由：`auth` · `children` · `content` · `progress` · `rewards` · `evaluation` · `recordings` |
| 后端内部 | 手写 SQL（无 ORM）· `security.py`(JWT) · `ratelimit.py`(内存限流) · `seed.py` · 启动时建表 + 幂等迁移 |
| 存储 | SQLite（WAL + busy_timeout + FK）· `backend/media/` |
| 运维 | cron（`/etc/cron.d/kids-*`）：每日 02:30 DB 快照 + media tar（留 14 天）· 每日 03:30 事件汇总 + 录音保留期清理（`scripts/maintenance.sh`）· 每 5 min 健康检查（含维护心跳反查）· systemd `Restart=always` |

### 关键数据流（三条，各自的可信边界不同）

```
① 内容（构建期单向生成）
   frontend/src/data/lessons.ts   ← 唯一人工书写源
        │ scripts/export-lessons.mjs（需人工记得跑）
        ▼
   backend/seed/lessons.json      ← git 跟踪
        │ 启动时 seed_lessons()
        ▼
   lessons.content_json           ← 生产数据
   ⚠️ 前端 content store 是「远端优先」：远端拿到就用远端，拿不到才回退本地静态包。
      → 种子过期时，后端旧内容会覆盖前端新内容（详见 ADR-001）。

② 进度/奖励（离线优先 + 服务端权威合并）
   localStorage（即时写）→ 3s 防抖 → PUT /progress → 后端按「只增不减」合并（权威）
   红线：存储键冻结、星级/贝壳/时长只增不减、_daily 取 max（PROGRESS-DATA.md §7）

③ 契约（生成期）
   backend/app/schemas.py → openapi.json → frontend/src/types/api.ts（生成物）
   CI 用 git diff --exit-code 拦截漂移 ← 本项目已有的一致性范式
```

## 2. 已经做对的（**勿回退清单**）

新成员或未来的自己最容易"顺手修正"的，正是这些**当时有意为之**的取舍。
每条附上"退化信号"，出现该信号说明有人改错了方向。

| # | 决策 | 为什么是对的 | 退化信号 |
|---|---|---|---|
| 1 | OpenAPI 作为**单一契约源** + 生成 TS 类型 + CI 防漂移 | 消灭了"前端手写 mock 与后端不符"这一整类问题；契约变更在 CI 可见 | `src/types/api.ts` 被手改；出现手写请求/响应类型 |
| 2 | 离线优先 + **服务端权威合并** | 孩子在电梯/车上/弱网仍能学；多设备不会互相覆盖 | 出现"本地覆盖云端"的分支；合并改为取最新时间戳（会让累计量变小） |
| 3 | 存储键名**冻结**（`kids-english-progress-v1` 等） | 改键名 = 孩子攒的星星贝壳全丢 | 有人"顺手规范化"键名 |
| 4 | hash 路由 | 静态托管（Pages / 任意子路径）零配置；无需 nginx rewrite | 改成 history 模式却未同步 nginx |
| 5 | 构建闸门进 CI（`guard-build` 强制部署模式 + `validate-data` 数据校验） | 防"资源 404"与"加课数据漂移"这类只在线上才暴露的错误 | 有人为了发版方便绕过 guard |
| 6 | 单 worker uvicorn + SQLite WAL | **有意的**单写者，避免多 worker 争抢写锁；WAL 让读不阻塞写 | 有人加 `--workers 4` 而没先迁 Postgres |
| 7 | 灾害恢复手册（STABILITY.md） | 同规模项目普遍没有——这决定了最坏情况是"半天恢复"还是"数据没了" | 改动配置后不同步手册 |
| 8 | 测试基线（前端 310 / 后端 60）+ 评测 mock | 让重构敢做 | 为过 CI 删测试 |

## 3. 三个扩展轴（把"可扩展"落到具体维度）

"可扩展"是空话，除非说清**往哪个方向扩**。这个系统只有三条真实扩展轴。

### 轴一 · 内容轴（7 课 → 30+ 课，加课 <1 天）

| 项 | 现状 | 目标态 |
|---|---|---|
| 加一课的动作 | 改 `lessons.ts` → 重跑导出 → 重导种子 → 发版 | 运营后台点几下（或至少：加课 = 加数据，不发版） |
| 当前瓶颈 | **一致性**：双源无防漂移闸门（ADR-001） | 单一事实源 + 自动化闸门 |
| 瓶颈何时发作 | 已经可发生（改课忘导出 → 线上"改不动"） | — |
| 不解决的后果 | 课程越多，出现"改了没生效"的概率越高，且极难定位（本地复现不出） | — |

### 轴二 · 玩法轴（6 题型 → 可独立演进/可分享）

| 项 | 现状 | 目标态 |
|---|---|---|
| 承载方式 | `/learn/:id/:type` 显式子路由 + 6 题型共用 `LessonView` 编排壳 | 题型成为可独立开发/测试/直达的单元 |
| 当前瓶颈 | **内聚**：题型语义与流程编排在同一个组件里 | 编排与题型分离 |
| 触发条件 | 题型 >8 个，或出现"跨课直达某玩法"的需求（REVIEW 已记为待触发项） | — |
| 评价 | 现在**不用动**。`useLessonFlow` 已把状态机抽出，拆分窗口还在后面 | — |

### 轴三 · 用户轴（3 家庭 → 开放注册 + 订阅）

| 项 | 现状 | 目标态（P3） |
|---|---|---|
| 身份 | 家庭口令 + email 登录，`families` 表 | 开放注册 + 账号治理 |
| 隔离 | `family_id` 贯穿 + 跨家庭 404（**已达标**） | 不变 |
| 能力缺口 | 无密码找回、无邮箱验证、无订阅/支付、无账号删除/导出 | 商业化必需 |
| 当前瓶颈 | **能力缺失**（不是架构错误）：`auth.py` 只有 register/login/gate/me | 按 §5 触发条件逐项补齐 |
| 反滥用 | 内存限流 10 次/分/IP（登录） | 多 worker 时失效 → 需外部化（见 §5） |

## 4. 架构风险清单（按"**何时开始痛**"排序，不是按严重程度）

排序依据是"触发它需要多久"——这比"理论上多严重"更有行动价值。

| # | 风险 | 何时开始痛 | 后果 | 应对 |
|---|---|---|---|---|
| **R1** | 内容双源无防漂移闸门，且前端"远端优先" | **现在（已可发生）** | 线上课程"改了不生效"，本地无法复现 | ADR-001（30 分钟） |
| **R2** | 后端手工 scp 上线；`deploy-server.sh` 的 exclude 指向已改名的 `server/`，会把 `.venv`/`.env`/`kids.db` 同步到服务器 | 下一次动后端 | 生产状态不可复现；**该脚本有能力用本地开发库覆盖生产库** | ADR-003 |
| **R3** | 迁移无版本记录（`_apply_migrations` 靠 PRAGMA 判断） | 第一次需要数据回填时 | 代码库与生产库静默错配；无法审计 | ADR-002 |
| **R4** | 线上白屏对开发者不可见（`errors.js` 只写本地环形缓冲） | **现在（已发生 2 次）** | 靠家长口述报障，定位靠猜 | ADR-004 |
| **R5** | 采集/时长无**查询面**（`progress.data_json` 是不透明文档） | 需要按词/按课聚合时 | 北极星算不出；任何统计要全量拉取到内存 | ADR-004（事件表旁路） |
| **R6** | 录音无保留期、无删除、**上传无大小上限**、库里存绝对路径 | 第一条真实录音入库 | 儿童语音无限期存储；一次大上传可拖垮单 worker | ADR-005（当前 0 条，成本最低） |
| **R7** | 内存限流 + 单 worker + 单机 | 开放注册 / 多 worker 时 | 多 worker 下限流失效；无 HA | §5 触发条件化 |
| **R8** | 账号治理缺口（无找回/验证/删除） | 第一个付费用户 | 无法支撑商业化 | §5 触发条件化 |

> 注意 R1/R2 已经**不是"潜在风险"**：R1 的失效链条当前就成立（只差一次"忘跑导出"），
> R2 里那个脚本当前就是危险状态。这两条是本文最建议立刻处理的。

## 5. 长期规划：阶段 → 架构触发条件

把 ROADMAP 的产品阶段翻译成"**架构上必须先成立的事**"。
每一行都给**可观测的触发信号**，而不是日期——日期会骗人，信号不会。

| 里程碑 | 产品动作（ROADMAP） | 架构前置条件 | 触发信号（可观测） |
|---|---|---|---|
| **P1** 体验闭环 | 资源上 CDN、评测接通、埋点 | ADR-001（防漂移）；ADR-004（事件表 + 错误上报） | 要写第一次北极星复盘时 |
| **P2** 内容引擎 | 30+ 课、自创 IP、加课 <1 天 | 内容源唯一化完成；"加课"成为可重复流程；ADR-005 已落地 | 单课产出耗时 > 0.5 天，或出现第二次"改了没生效" |
| **P3** 商业验证 | 订阅分层、开放注册 | ADR-002 + ADR-003 **必须已完成**（否则改表即事故）；账号治理（找回/验证/删除/导出）；支付回调幂等 | 第 1 个非亲友家庭要付费 |
| **P4** 增长复制 | 多端、IP 衍生 | 见下方迁移表；媒体转 OSS；多 worker | 见下方触发条件 |

### 迁移触发条件（到点才做，不到点坚决不做）

| 变更 | 触发条件（满足任一） | 为什么不是现在 |
|---|---|---|
| SQLite → PostgreSQL | ① 需要 >1 个 uvicorn worker（因请求排队/CPU 打满）；② 跨孩子/跨课聚合查询进入热路径；③ 单库 >5GB 或 media 与 DB 同盘写放大明显 | 当前 7 表 / 3 家庭；WAL 已解决读阻塞；迁移会引入连接池、迁移工具、运维复杂度 |
| media → 对象存储（OSS） | `backend/media/` > 2GB；或每日备份耗时 > 1 分钟；或需要 CDN 回放 | 当前 0 条录音 |
| 引入 ORM / alembic | 表数 > 12；或出现第一个需要数据回填的迁移 | 手写 SQL 在本规模更可读；ADR-002 的版本化列表足够 |
| 限流外部化（Redis 等） | uvicorn worker 数 > 1（内存限流按进程隔离，届时失效） | 单 worker 内存限流正确且零依赖 |
| 服务拆分 / 微服务 | 某个域出现**独立的伸缩或发布需求** | 当前无任何域有此需求；拆分只会把一次网络调用变成一次故障点 |

## 6. 明确不做（反"架构宇宙飞船"清单）

写下"不做什么"比写下"做什么"更能保护项目。以下每条都曾出现在同类项目的"最佳实践"清单里。

| 不做 | 理由 |
|---|---|
| 微服务 / K8s / 服务网格 / 消息队列 | 面向 5-10 个付费家庭的产品，**运维复杂度是最贵的成本**，且当前的团队规模（1 人）无法承担其故障模式 |
| 引入 ORM | 手写 SQL 在本项目规模下更可读、零依赖、便于审计；缺的是**版本化迁移**，不是 ORM |
| CQRS / 事件溯源 | `progress` 的"只增不减合并"已是够用的领域规则。上 ES 会把最简单的路径（读一个 blob）变复杂，且没有收益场景 |
| 多租户基础设施（配额/计费/独立库） | `family_id` 隔离已达标。等到真的对外开放注册再谈，避免为想象中的规模付费 |
| 把 `progress.data_json` 提前拆表 | 拆表会破坏"客户端即文档模型"的对齐，收益（查询）已由 ADR-004 的事件表旁路解决。**保留文档模型是刻意的可逆性投资** |
| 自建账号体系之外的复杂权限模型（RBAC 等） | 当前只有两个角色：家庭 / 非本家庭。乘法关系不需要权限矩阵 |
| 全量 ESLint 重排 | 属工程卫生而非架构；应以增量方式落地（只对改动文件），不阻塞交付 |
